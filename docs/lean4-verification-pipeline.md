# Lean4 Formal Verification Pipeline

Documentation for the Charon/Aeneas → Lean4 verification infrastructure that
covers selected `gf2-core` and `gf2-algebra` arithmetic paths.

> **`scripts/verify-lean.sh` is the single source of truth for this pipeline.**
> It is the executable definition of every extraction flag, tool pin, and
> post-processing pass, and its header comment records why each workaround is
> load-bearing. This page mirrors that script and
> [`proofs/WORKAROUNDS.md`](../proofs/WORKAROUNDS.md); where this page and the
> script disagree, the script is correct and this page is the defect. Change the
> script first, then update the mirror here in the same commit.

## Overview

We translate Rust source into Lean4 for formal verification using:

1. **Charon** — compiles Rust to LLBC (Low-Level Borrow Calculus), an
   intermediate representation.
2. **Aeneas** — translates LLBC to pure Lean4 code.
3. **Lake** — the Lean4 build system that type-checks the generated code and the
   hand-written proofs on top of it.

`scripts/verify-lean.sh` runs all three end to end, over two independent
extractions: `gf2-core` into `proofs/Gf2Core/`, and `gf2-algebra` into
`proofs/Gf2Algebra/`.

### What is verified

| Module | Status | Notes |
|---|---|---|
| `gf2_core::gfp` (prime field `Fp<P>`) | Verified | Montgomery multiplication, field ops, const generics; the live `use_specialized_storage` classifier stays transparent |
| `gf2_core::gfpn::{quadratic,cubic}` (`QuadraticExt`, `CubicExt`) | Verified | Tower extensions over the `ExtConfig` trait |
| `gf2_core::gf2m::mul_raw` | Verified | Monomorphized `u64` schoolbook GF(2^m) multiplication |
| `gf2_algebra::packed::{bipedal3,packed5,packed7}` | Verified | Packed F_3 / F_5 / F_7 arithmetic; `packed7`'s LUTs are axiomatized (Path B) |
| `gf2_algebra::gray` | Extracted | Gray-code iteration, consumed by the Ryser development |
| `gf2_core::field` traits | Extracted, opaque bodies | `FiniteField`, `ConstField` declarations only |
| `gf2_core::gfpn::quotient`, `gf2_core::gfpn::batch` | Opaque | Runtime modulus and `Vec` storage; vectorized batching layer |
| `gf2_core::gf2m::{field,generation,uint_ext,barrett}` | Opaque | Runtime field parameters, `Arc<FieldParams>`, sealed traits |
| Everything else | Opaque or excluded | Out of scope (bitvec, matrix, SIMD dispatch, IO, …) |

The authoritative transparent/opaque split is the flag list in
`scripts/verify-lean.sh` reproduced under [Stage 1](#stage-1-charon-extraction);
the table above is a reading aid, not a second source.

### Generated files

Regenerated by the pipeline; do not hand-edit except where noted.

| File | Contents |
|---|---|
| `proofs/Gf2Core/Types.lean` | Type definitions (`Fp<P>`, `MontConsts<P>`, `QuadraticExt`, `CubicExt`, trait structs) |
| `proofs/Gf2Core/Funs.lean` | Function bodies translated from Rust |
| `proofs/Gf2Core/TypesExternal.lean` | Opaque external type axioms, regenerated from the template each run |
| `proofs/Gf2Core/FunsExternal.lean` | **Hand-edited.** Concrete defs replacing Aeneas axioms; seeded from the template on first run only, never overwritten |
| `proofs/Gf2Core/{Types,Funs}External_Template.lean` | Aeneas-generated templates |
| `proofs/Gf2Algebra/*` | The same set for the `gf2-algebra` extraction; its `FunsExternal.lean` carries no hand-edits and is always regenerated |

## Pipeline stages

Run everything:

```bash
./scripts/verify-lean.sh
```

Build only the committed Lean sources, with no Charon or Aeneas needed:

```bash
cd proofs && lake build
```

The `lake-build` quality gate runs `scripts/lake-build-strict.sh`, which wraps
`lake build` and additionally fails on a `declaration uses 'sorry'` warning in
any hand-written file under `proofs/Gf2Core/Proofs/` or
`proofs/Gf2Algebra/Proofs/`. Aeneas-generated files keep their extraction
artefacts and are exempt.

Why the flags look like this:

- **`--start-from` instead of the whole crate.** Charon `487f0320` can overflow
  its stack when starting from `crate`, so extraction starts at the
  proof-relevant modules only (`proofs/WORKAROUNDS.md`, "ExtConfig associated
  const extraction").
- **`--rustc-arg=--cfg=verify_lean`.** Under that cfg, `ExtConfig` exposes the
  non-residue as a trait method `NON_RESIDUE()` rather than an associated const
  whose type is `Self::BaseField`, a shape Charon rejects before Aeneas sees the
  arithmetic. The same cfg turns off the SIMD fast-path overrides on the
  `Fp::FiniteField` impl (`crates/gf2-core/src/gfp/mod.rs`) so the trait
  defaults extract instead; `scripts/verify-lean.sh` enumerates them. Normal builds keep the associated-const API and the
  fast paths.
- **`gf2m` submodule-by-submodule.** `--opaque gf2_core::gf2m` would stop Charon
  exploring the module at all, so `mul_raw` stays transparent by opaquing its
  siblings individually.
- **The three `batch_*_mersenne31` functions, not the whole `specialized`
  module.** Aeneas no longer ships the slice-iterator `zip` instances those SIMD
  helpers need; the module's scalar reductions are called by transparent `gfp`
  code and stay in.
- **`gf2_core::*` opaque in the second invocation.** The packed arithmetic never
  reaches `Fp`/`FiniteField` at runtime, but Charon would otherwise pull those
  trait impls in transitively and surface operator wrappers with opaque bodies.
- **The `packed7` LUTs opaque.** Path B of the D6 design: the three 64 KiB
  compile-time tables are external constants whose contents the Lean proof
  axiomatizes against a source-faithful characterisation, cross-validated by the
  exhaustive Rust `test_*_lut_contract_exhaustive` tests.

Benign warnings are expected on both invocations — residual `FiniteField::Wide`
warnings on the opaque `field` trait, and generic-arity warnings on
`QuadraticExt`/`CubicExt` that Aeneas resolves through Lean implicit-argument
inference. `scripts/verify-lean.sh` and `proofs/WORKAROUNDS.md` record which
classes are expected; neither records a count, because the counts move with the
toolchain.

### Stage 2: Aeneas translation

```bash
aeneas -backend lean -dest proofs/Gf2Core   -split-files target/charon/gf2_core.llbc
aeneas -backend lean -dest proofs/Gf2Algebra -split-files target/charon/gf2_algebra.llbc
```

Aeneas can exit non-zero while still emitting usable partial files for functions
it cannot fully translate. The script tolerates that and instead checks that the
required outputs (`Types.lean`, `Funs.lean`, `FunsExternal_Template.lean`, and
for `gf2-algebra` also `TypesExternal_Template.lean`) exist, failing only when
one is missing.

### Stage 3: Post-processing

Five passes run after Aeneas, in this order.

#### `scripts/fix-aeneas-dupes.py`

Three passes over the generated `Types.lean` and `Funs.lean`:

- `dedup_fields` — the `FiniteField` trait bounds `Self`, `Characteristic`, and
  `Wide`, so Aeneas emits three fields all named `corecloneCloneInst`. The pass
  renames the second and third with `Characteristic` and `Wide` suffixes and
  rewrites the projection paths on the following value lines to match.
- `inline_default_methods` — Aeneas at this pin emits no sibling definitions for
  default trait methods, so the pass inlines them at instance-dictionary call
  sites.
- `silence_extraction_sorry` — injects `set_option warn.sorry false` into the
  generated `Funs.lean` so extraction artefacts do not trip the strict
  `lake-build` gate. Hand-written proofs are unaffected and still fail on
  `sorry`.

#### Inline `Types.lean` fixup

The narrowed start set can leave an opaque `gf2m` external type in
`TypesExternal.lean` while also generating the out-of-scope `UintExt` trait in
`Types.lean`. The script strips the generated declaration and keeps only the
opaque axiom; no verified `gfp`/`gfpn` code projects fields from `UintExt`.

#### `scripts/fix-aeneas-sorrys.py`

Restores known-good bodies for `gfpn` functions this Aeneas/Charon pair cannot
translate (the "new value doesn't have the same type as its destination"
assertion on `QuadraticExt`/`CubicExt` operator impls), and opaques a small
`OPAQUE_DEFS` set: the non-`Wide` `gfpn` `CoreCmpEq` instances, the cubic
`Display::fmt`, and the `ConstField` instance dictionaries for
`{Cubic,Quadratic}Ext`. None of those is an arithmetic proof target — the proofs
use the separate `.order`/`.zero`/`.one` sub-definitions.

#### External-file handling

`TypesExternal.lean` is regenerated from its template on every run. When the
template mentions the sealed `UintExt` trait, the script prepends that one
opaque type axiom.

`FunsExternal.lean` is **hand-edited** for `gf2-core` and is seeded from the
template only when absent, never overwritten. Its concrete definitions currently
replace the Aeneas axioms for `wrapping_neg`, `U128` `add` and `add_assign`,
`Option::expect`, and `Option::map`; the rest of the file stays axiomatic
(`assert_receiver_is_total_eq`, `hash`, `is_power_of_two`, `trailing_zeros`,
`U64::BITS`, `U128::saturating_mul`, `Option::and_then`, and the `Try` branch).
`overflowing_sub` is no longer hand-defined — Aeneas provides it natively as a
pure `U64 → U64 → (U64 × Bool)` consumed through `lift`, and the old
`Result`-returning override conflicted with it.

The `gf2-algebra` `FunsExternal.lean` carries no hand-edits and is always
regenerated from its template.

#### `scripts/fix-aeneas-gf2algebra.py`

Rewrites the transitively-extracted `gf2_core::gfp::Fp` operator wrappers as
axioms, from an explicit ten-wrapper allowlist. Those impls are pulled in
because `PackedField<Fp<3>>` has `Fp<3>: FiniteField` as a parent bound, but the
packed ops never elaborate them; their bodies reference definitions that are
opaque in this narrow extraction and would otherwise surface as `Unknown
constant`. The pass stops on missing, duplicate, or unknown dictionaries so
extraction drift cannot silently widen the workaround.

### Stage 4: Lake build

```bash
cd proofs && lake build
```

Type-checks the generated Lean and the hand-written proofs on top of it. When
`AENEAS_LEAN_DIR` is set, the script first repoints `lakefile.lean` and
`lake-manifest.json` at that path, which is how CI substitutes its own Aeneas
checkout.

## Charon patch

One project-local patch applies on top of `487f0320`, in
`charon/src/transform/normalize/expand_associated_types.rs`.

**Implied-clause constraint propagation** in `compute_trait_modifications`:
upstream propagates `type_constraints` from direct `parent_clauses` but not from
`implied_clauses`. For a trait like `ConstField: FiniteField`, where the
constraint on associated types flows through an implied clause, the omission
produced 86 "Could not compute the value of an associated type" warnings on the
`gfpn` quadratic and cubic arithmetic. The patch propagates from
`tr.implied_clauses` with the same logic used for `parent_clauses`. A copy is
preserved at
`dev/active/charon-patch-backup-2026-05-15/implied-clause-rebased-487f0320.patch`.

Three earlier patches are **obsolete** as of the 2026-06-30 upgrade — upstream
Charon now handles all three cases, and `gfpn` extraction is clean without them:

| Obsolete patch | What it did |
|---|---|
| HRTB erase | Replaced `move_from_under_binder()` with `.erase()` at three sites so higher-ranked `for<'a>` bounds stopped panicking during associated-type expansion |
| `SelfClause`/`Local(0,0)` unification | Added a bidirectional fallback in `lookup_type_replacement()` because Charon represented `Self` both ways in different codepaths |
| `pretty/fmt_with_ctx.rs` assert removal | Dropped a formatting assertion that fired on the extracted trait hierarchy |

Their test cases and backups remain in
`dev/active/charon-patch-backup-2026-05-15/`.

## Const generics

`Fp<const P: u64>` extracts without monomorphization wrappers: Charon handles
const generics natively and Aeneas translates `P` as a Lean parameter
`(P : Std.U64)`.

## Regenerating after Rust changes

When Rust source under `gfp/`, `gfpn/`, or `gf2m/mul_raw.rs` changes, or when
any `gf2-algebra` packed module changes:

```bash
./scripts/verify-lean.sh
git add proofs/Gf2Core/ proofs/Gf2Algebra/
```

If a step fails on `main`, file an issue rather than reverting a workaround —
each one is load-bearing for the current Charon/Aeneas/Lean trio.

## Troubleshooting

### "Could not compute the value of an associated type"

The implied-clause patch was lost during a Charon rebuild. Reapply it from the
backup and reinstall.

### "field has already been specified" in the lake build

`scripts/fix-aeneas-dupes.py` failed to detect a `FiniteField` block. Check
whether the Aeneas output format moved the `:= {` line further from the
`field.traits.FiniteField` reference than the pass's 10-line lookback window
allows.

### Type mismatch on `Characteristic`/`Wide` fields

The projection-path fixup in `scripts/fix-aeneas-dupes.py` did not fire. Ensure
the pass is seeing fresh Aeneas output: rerunning it by hand on already-processed
files skips the fixup silently. The pipeline script sequences this correctly.

### `TTraitType` arity mismatch when building Aeneas

The nested Charon submodule under `/data/aeneas-build/` is not at `487f0320`.
Check it out to the pin and rerun `dune build`.

cd /data/aeneas-build/charon
RUSTUP_TOOLCHAIN=nightly-2026-06-01 cargo install --path charon
