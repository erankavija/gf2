## Traps — do not repeat these (NEW this session; s1+s2+s3 traps still apply)

- **Do NOT run a `cargo-ci`/`tests` gate immediately after a `./scripts/cargo-ci.sh` pre-warm finishes — the loadavg spike from the just-finished build flakes the 5s-limit nextest** (timing-sensitive subprocess tests, and the pre-existing `typestate_rejects_out_of_order_calls` trybuild test which tips nextest's 10s limit under load). This bit cargo-ci on `5f12e7ff` r5/r6 and r8 (failed once, PASSED on immediate re-run — same warm build). Lesson refined from s2: it is NOT only instantaneous %CPU; the loadavg tail after a build burst is enough. **Re-running the same gate once after a flake passes.** Also: the `cargo-ci.sh` result.json only records the `check/test/clippy/fmt` step summary, NOT the failing test name — reproduce with `cargo nextest run -p gf2-sim --release --profile ci` to identify a real failure vs a flake.
- **`bg3` (a game/external process) intermittently consumes 140–340% CPU** and was the cause of 3fcb7025's invalid benchmark (s2) and this session's gating flakes. ALWAYS `cat /proc/loadavg` + `ps -eo pcpu,comm --sort=-pcpu | head` before any throughput measurement or perf-gate; `rocm-smi --showuse` for GPU. The f6004add throughput was re-measured at loadavg 0.42 (clean) BEFORE bg3 returned — valid. For `a930be7f`'s ≥3×-CPU-24 perf gate, you MUST wait out bg3.
- **The codex code-review gate re-reviews ALL of an issue's code every run and surfaces a DEEPER finding each round** (5f12e7ff: 5→4→4→2→1 across formal rounds; f6004add: passed pre-review then formal gate found 4). Budget for it; the lead must holistically pre-audit. The mandated adversarial pre-reviewer is NOT an oracle (it PASSED 5f12e7ff and f6004add; the formal gate then failed both). Always still run it, but treat the formal gate as authoritative.
- **"Kill DURING fsync" cannot be instrumented from user space** — a pre-`sync_all` hook necessarily runs before the syscall; proving the process is inside `fsync` needs ptrace. crit-3 was user-amended to "kill mid-flush: after tmp bytes written, before the atomic rename" (the real durability invariant). Also: `/tmp` is **tmpfs** on this host (`sync_all` ~1µs no-op) — fsync-timing tests MUST use `CARGO_TARGET_TMPDIR` (real ext4; 64 MiB `sync_all` ≈ 673 ms).
- **Cross-simulator resume byte-identity is architecturally impossible AND was deleted.** A checkpoint produced by the legacy `SimulationRunner` (rand 0.8) can never resume byte-identically in `gf2-sim` (rand 0.9, global-frame keying), and its config_hash can never match `blake3(live PipelineConfig)`. The CLEAN-CUT decision removed all v1 migration. Do NOT re-introduce a `checkpoint_migrate` tool or any v1 path (design §4 + epic Q5 record the removal). The checkpoint reader is v2-only.
- **The CPU within-SNR path has NO per-worker RNG streams** (3fcb7025 global-keys every frame on `worker_offset(seed,snr,0,g)` for cross-worker-count byte-identity). It resumes via the GLOBAL `frames_completed`, NOT per-worker `rng_word_pos`. `worker_states[].rng_word_pos` is recorded in §4-formula form (real `worker_idx`) ONLY for the future Phase C fixed-partition executor (`571c11c4`). Design §4 drain contract was amended to document this split. Do NOT "fix" the CPU path to per-worker-stream-restore — it would break 3fcb7025's [hard] byte-identity.
- **A perf criterion that names `c0b1702d` (full-frame 1.6216 fps) is a category-confused comparator for a stage-only kernel.** f6004add (noise-only) vs full-frame = meaningless 11507×; the honest apples-to-apples is GPU-noise vs CPU-noise (14.91×). crit-3 was user-amended to the AWGN-step baseline. **`a930be7f` (GPU LDPC BP) and `d3f1616a` (GPU demap) likely have the SAME issue** — their perf gates reference baselines; check at dispatch whether the comparator is apples-to-apples (decode-vs-decode, demap-vs-demap) or escalate to amend BEFORE the worker writes a confused receipt. `a930be7f`'s "≥3× CPU-24" — confirm CPU-24 means the 24-thread DECODE throughput, not full-frame.
- **`gf2-kernels-hip` is UPSTREAM of `gf2-sim`** (gf2-sim depends on it, not vice versa). A test needing BOTH a GPU kernel AND `gf2_sim::parallel::worker_offset` must live in `gf2-sim` (it can call both), NOT in gf2-kernels-hip (which would have to duplicate the seek scheme → SSOT FAIL). All future GPU byte-identity tests go in gf2-sim.
