## Question 3 — Large-n cross-check infeasibility

**Chosen**: "Block-decomposable cross-check (Recommended)"

Reasoning the lead surfaced in the AskUserQuestion text:
- `permanent_ryser` itself caps at `n <= 63` so it cannot oracle `n=65..128`.
- `2^65` to `2^128` Gray-code steps is wholly infeasible (>10^10 seconds
  single-core at any realistic step rate).

Implementation (per the chosen option):
- For each `n ∈ {65, 72, 96, 128}` the test builds block-diagonal matrices
  `[A_{n_0} ⊕ I_{n - n_0}]` with random `n_0 ∈ {10, 11, 12}`. The bipedal
  multi-word permanent of the full matrix factorises algebraically to
  `permanent_ryser(A_{n_0}) * permanent(I_{n - n_0}) = permanent_ryser(A_{n_0})`.
- Tests carry `#[ignore = "sim: large-n cross-check"]` because the multi-word
  permanent still walks the full `2^n` Gray-code subset space at runtime.
  Test bodies document the oracle so the assertion is valid against a
  future-speedup machine.
- Fast-tier cross-checks call `permanent_bipedal3_multiword` directly
  (release skips its `debug_assert!(n > 64)`) and verify bitwise
  equality with `permanent_ryser`. **As shipped: 850 random matrices
  total across `n ∈ {2, 5, 8, 16, 20}`** (200 trials each at n ∈ {2, 5, 8, 16},
  50 trials at n=20). The originally-considered `n ∈ {24, 32, 48, 60}`
  cells exceed the 5 s fast-tier budget, so they carry
  `#[ignore = "slow: ..."]` with 5 / 2 / 5 / 2 trials respectively.
  An earlier draft of this doc mentioned the wider set
  `n ∈ {2, 5, 8, 16, 24, 32, 48, 60}` with `≥ 100` matrices; that was
  the lead's pre-implementation budget estimate, and the actual shipped
  numbers above supersede it.
