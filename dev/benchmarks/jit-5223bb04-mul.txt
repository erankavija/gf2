Implementation/path statement:
- BitMatrix::mul_row_xor_dispatch is the direct non-M4RM row-XOR accumulator.
  It resolves crate::kernels::ops::resolve_xor_inplace once before scanning lhs
  set bits, then calls the resolved function pointer for each selected rhs row.
- alg::m4rm::multiply keeps choose_k_block unchanged. When choose_k_block
  degenerates to 1, table precomputation has no reuse advantage, so the
  non-M4RM row-XOR fallback handles the product.
- R1 moved the M4RM output allocation after the k_block == 1 fallback branch, so
  the production fallback no longer allocates and discards an unused M4RM output
  before calling BitMatrix::mul_row_xor_dispatch. The M4RM crossover and
  choose_k_block logic are unchanged.
- For matmul_square/1024 and /2048, choose_k_block remains 8 (stride_words 16
  and 32 respectively; 256-entry tables fit under the existing 64 KiB target),
  so those design sizes still use the M4RM route rather than the non-M4RM
  fallback. They are retained only as a non-regression smoke check for the
  pre-existing M4RM path.

Dedicated fallback benchmark:
- Criterion leaf: matmul_row_xor_fallback/{scalar_backend,dispatch_helper,production_mul}/512x1x8192
- Shape: lhs 512x1, rhs 1x8192, output row width 8192 bits = 128 u64 words.
- Fallback proof:
  - choose_k_block(k=1, n=8192) must return 1 because the selector never
    returns a block size greater than k.
  - alg::m4rm::multiply therefore branches to BitMatrix::mul_row_xor_dispatch.
  - stride_words = 8192 / 64 = 128, which is >= the 8-word SIMD threshold, so
    resolve_xor_inplace selects LogicalFns::xor_fn when the simd feature detects
    an AVX2 backend.
- Benchmark variants:
  - scalar_backend: same row-XOR fallback loop, but each selected rhs row is
    accumulated with SCALAR_BACKEND.xor.
  - dispatch_helper: test-support hook calling BitMatrix::mul_row_xor_dispatch
    directly.
  - production_mul: public production path through alg::m4rm::multiply and its
    k_block == 1 fallback branch.

Assembly evidence:
- crates/gf2-core/src/matrix.asm.txt contains the production multiply branch to
  BitMatrix::mul_row_xor_dispatch for the 512x1x8192 fallback shape.
- The same artifact shows the row-XOR fallback call site: stride_words is checked
  against the 8-word cutoff, LogicalFns::xor_fn is loaded from bundle offset
  0x10, stored in a stack slot, and called from the set-bit loop.
- The inspected AVX2 xor_fn kernel contains vector XOR instructions. On this
  toolchain the exact full-vector XOR mnemonic is vxorps for the xor_fn body;
  vxorps is bitwise-equivalent on YMM registers and is the inspected vector XOR
  for this fallback call site. Adjacent vpxor mnemonics in the same binary are
  not used as the proof for this call site.
