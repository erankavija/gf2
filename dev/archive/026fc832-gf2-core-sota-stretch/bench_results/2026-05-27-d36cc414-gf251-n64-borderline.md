## § 1 — Background

Wave 7b's blocked echelon (`869ce43b`), invert (`8df0c501`), and solve (`6613abf4`)
implementations close large blocks of the A8 scorecard but each leaves 1-2 cells
at GF(251)/n=64 (and one cell at GF(251)/n=256 deficient invert) just above the
1.5× threshold:

| A8 row | Op | Field/n/regime | gf2 median ns | fflas ref ns | Ratio | Source |
|---|---|---|---:|---:|---:|---|
| 23 | echelon | GF(251)/64/deficient | 103 100 | 64 304 | 1.60× | `869ce43b` |
| 37 | invert | GF(251)/64/uniform | 169 070 | 110 988 | 1.524× | `8df0c501` |
| 40 | invert | GF(251)/256/deficient | 1 090 000 | 652 212 | 1.672× | `8df0c501` |
| 51 | solve | GF(251)/64/uniform | 47 131 | 28 150 | 1.674× | `6613abf4` |
| 52 | solve | GF(251)/64/deficient | 33 016 | 19 110 | 1.728× | `6613abf4` |

The cluster 1.524×–1.728× hinted at a common per-call dispatch overhead, hence
the hypothesis that a single optimization could close all five cells.

The decomposition below falsifies that hypothesis: the dominant cost in each
cell is **the panelized PLE itself plus the recursive TRSM with a wide RHS**,
not a fixable Rust-layer dispatch overhead.

## § 2 — Methodology

### Profiling approach

`perf` paranoid level on the host is `2`, blocking unprivileged `perf record`
sampling. We fall back to **manual instrumentation**: a new ignored test
`test_gf251_n64_borderline_cost_decomposition` in
`crates/gf2-core/src/field/inverse.rs` wraps each phase of the production
code path with `std::time::Instant::now()` boundaries and prints per-phase
wall-time CSV to stderr.

Each cell is warmed up with 3 calls, then sampled 5 trials. The test also
emits a **control 5-trial whole-op wall-time block** so we can verify the
decomp sums are within a small inflation factor of the integrated path
(boundary instrumentation forces re-loads at phase boundaries that the
optimizer would otherwise elide).

### Cell construction

Identical to the wave-7b harnesses (same per-cell seed derivation as
`field::ple::tests::measure_echelon_cell` /
`field::inverse::tests` benches):

```text
seed = P * 0x9E37_79B9 + n + (0x1234 if deficient else 0)
deficient: A = random(n, n/2, seed) * random(n/2, n, seed ^ 0xCAFE)
uniform:   A = random_fp_invertible(n, seed)
```

### Run

```bash
./dev/benchmarks/ccx1-bench-flock.sh \
  cargo test -p gf2-core --release --all-features --lib -- \
  --nocapture --ignored \
  field::inverse::tests::test_gf251_n64_borderline_cost_decomposition \
  2>&1 | grep -E 'decomp|whole|BEGIN|END' \
  > dev/bench_results/2026-05-27-d36cc414-gf251-n64-borderline.csv
```

Raw per-trial data: `2026-05-27-d36cc414-gf251-n64-borderline.csv`.

### Phase definitions

**Echelon** (`row_echelon` → `ple` + builders + `trsm_lower`):

| Phase | Description |
|---|---|
| `ple` | `self.ple()` — panelized PLE through `try_panel_base_dispatch` |
| `pad_l_full` | Build `m×m` unit lower-triangular L_full (pad L with identity tail) |
| `build_pt` | Build `m×m` Pᵀ from permutation indices |
| `trsm_lower` | `trsm_lower(L_full, P_T)` solving `L_full · X = Pᵀ` in place — n×n RHS |
| `build_e_full` | Build `m×n` E_full (zeros below rank) |

**Invert** (`blocked_inv_panelized`):

| Phase | Description |
|---|---|
| `ple` | `a.ple()` — panelized PLE |
| `rank_deficient_early_exit` | Return None branch (taken for row 40) |
| `build_identity` | Allocate n×n identity scratch |
| `trsm_lower` | `trsm_lower(L, I)` — n×n RHS |
| `trsm_upper` | `trsm_upper(E, Y)` — n×n RHS |
| `col_perm` | `out[i, j] = y[i, perm[j]]` final permutation pass |

**Solve** (`solve` → `solve_batch`):

| Phase | Description |
|---|---|
| `wrap_b` | Wrap `FieldVec` into `n × 1 FieldMatrix` |
| `ple` | `a.ple()` |
| `rank_deficient_early_exit` | Return None branch (taken for row 52) |
| `row_perm` | `perm.inverse().apply(&b_mat)` — Pᵀ · B |
| `trsm_lower` | Blocked TRSM (falls back to recursive at n=64) — n×1 RHS |
| `trsm_upper` | Blocked TRSM — n×1 RHS |
| `unwrap` | Unwrap `FieldMatrix` result back to `FieldVec` |

### Instrumentation overhead

Each `Instant::now()` pair adds ~50-150 ns at sub-microsecond resolution.
Phase boundaries also defeat optimizer inlining across phases. The
decomposition test reports both decomp sums and whole-op control medians;
the inflation factors observed are:

Inflation factors are tight (under 11% across all five cells). Phase

## § 3 — Cost Breakdown per Op

### Row 23 — echelon/GF(251)/64/deficient

Phase median ns (5 trials):

| Phase | Median ns | % of decomp |
|---|---:|---:|
| ple | 35 370 | 32.5 |
| pad_l_full | 2 840 | 2.6 |
| build_pt | 380 | 0.3 |
| trsm_lower (m×m RHS) | 67 500 | 62.0 |
| build_e_full | 2 770 | 2.5 |
| **whole-op median** | — | **98 280** |

**Dominant cost: `trsm_lower(L_full, Pᵀ)` at 62% of total**, with PLE at 33%.
The TRSM has a 64×64 RHS because `Pᵀ` is m×m, so the call is recursive
bisection down to `TRI_BASE_THRESHOLD = 8` with multiple internal GEMM
calls. At n_rhs=64 these inner GEMMs hit `fp_small_try_gemm_classical`
but the recursion fan-out and scalar `trsm_lower_base` work at m=8
together dominate.

### Row 37 — invert/GF(251)/64/uniform

| Phase | Median ns | % of decomp |
|---|---:|---:|

### Row 40 — invert/GF(251)/256/deficient

| Phase | Median ns | % of decomp |

## § 4 — Summary Table — Dominant Cost per Cell

| Row | Cell | Dominant phase | Phase % | Hypothesis: "single common per-call overhead"? |
|---|---|---|---:|---|
| 23 | echelon/GF(251)/64/def | trsm_lower (m×m RHS) | 62% | **No** — TRSM, not PLE |
| 37 | invert/GF(251)/64/uni | 2× TRSM (n×n RHS) | 74% combined | **No** — TRSM, not PLE |
| 40 | invert/GF(251)/256/def | ple | ~100% | **Yes (PLE-bound)** |
| 51 | solve/GF(251)/64/uni | ple | 83% | **Yes (PLE-bound)** |
| 52 | solve/GF(251)/64/def | ple | 99.8% | **Yes (PLE-bound)** |

The five cells decompose into **two structurally distinct sub-clusters**:

- **Cluster 1 (TRSM-dominated):** rows 23, 37 — n×n or m×m RHS TRSM at n=64
  is recursive bisection that bottoms out in `trsm_*_base` (scalar
  arithmetic at m ≤ `TRI_BASE_THRESHOLD = 8`). The TRSM cost is in the
  recursion fan-out and the scalar base case, NOT in dispatch overhead.

- **Cluster 2 (PLE-dominated):** rows 40, 51, 52 — at n=64 with sparse
  RHS (n×1) or rank-deficient n=256, the PLE driver itself is at-floor.
  The panelized PLE kernel
  (`gf2_kernels_simd::fp_small_ple::ple_panel_base_safe`) is already
  AVX2-optimized. The remaining Rust-layer overhead (`build_small_prime_tables`
  via OnceLock, `Vec<u8>::with_capacity(m·win)` packing buffer,
  `apply_row_perm_outside_window` cycle walker) was profiled in §5 and
  contributes <2% of the PLE wall time.

## § 5 — Why a Dispatch-Path Optimization Does Not Close the Gap

### What "dispatch overhead" could plausibly be removed

The issue hypothesised a per-call setup cost dominating at n=64. Candidates
(audited against the production code paths):

1. **`build_small_prime_tables::<251>()`** —
   `crates/gf2-core/src/gfp/simd_ops.rs:1705`. Already cached via
   `SMALL_PRIME_TABLE_SLOTS` `OnceLock`. First-call cost: O(P) REDC
   operations. Subsequent calls: single atomic load. Cost per PLE call
   at GF(251)/n=64 (steady state): a few ns.

2. **`Vec<u8>::with_capacity(m * win)`** in `fp_try_ple_panel_base`
   (`crates/gf2-core/src/gfp/simd_ops.rs:2609`). For m=64, win=64:
   4 KB allocation. Could be replaced with a thread-local scratch.
   Saved per call: ~100 ns malloc + ~100 ns free + cache hit on reused
   buffer ≈ 0.5% of PLE wall time at n=64.

3. **`apply_row_perm_outside_window`**
   (`crates/gf2-core/src/gfp/simd_ops.rs:2714`). For the n=64 panelized
   PLE the column window spans the full matrix width (col_lo=0,
   col_hi=parent_cols=64) so the function returns at line 2722-2725
   (`if col_lo == 0 && col_hi == parent_cols { return }`). Zero cost.

4. **`apply_perm_indices`** (line 2843) — `perm.to_vec()` allocates
   `m * 8 = 512` bytes at n=64. Single call per panel. Cost: ~50-100 ns
   ≈ 0.3% of PLE wall time.

5. **Working clone in `FieldMatrix::ple`**
   (`crates/gf2-core/src/field/ple.rs:1166`). `self.clone()` allocates
   `n × n` `Vec<F>` plus copies content: 32 KB for GF(251)/n=64. Cost:
   ~3-5 µs (~10-15% of PLE wall time).

**Best-case savings from removing all of the above: ~6-8 µs out of 38 µs PLE
= ~16% PLE wall time = ~2-3 µs reduction at the op level.** That improves
the worst cell (row 52, 33 µs → ~30 µs) but the corresponding fflas reference
is 19 µs — the ratio after the optimization is still ~1.6×.

### What is left is structural

Once the Rust-layer overhead is stripped, the PLE wall time is dominated by
the AVX2 byte-lane kernel itself. The kernel
(`gf2_kernels_simd::fp_small_ple::ple_panel_base_safe`) packs the input to
canonical bytes, runs the row-major axpy Schur update with `_mm256_*`
intrinsics, and unpacks back to Montgomery storage. At m=n=64 the kernel
processes ~64³ = 262 K byte ops; AVX2 throughput on this kernel is ~3-5
Gops/s effective (the kernel is bound by gather/scatter latency, not
multiply throughput).

The fflas reference at GF(251)/n=64 PLE is 31.5 µs — implying fflas-ffpack
uses a different elimination algorithm at small n (likely scalar-pivot with
classical sgemm-based Schur updates that hit the float-modular BLAS
cascade). Closing this gap would require either:

- A different PLE algorithm for n < 128 (e.g., a direct scalar pivot path
  similar to fflas's small-matrix shortcut), or
- A wider PLE kernel that processes 64 pivots in one shot using packed F32
  arithmetic instead of byte lanes.

Both options are substantial new kernels, well beyond the scope of "a
dispatch-path optimization."

### TRSM cluster (rows 23, 37) is similarly structural

`trsm_lower_inner(64, RHS=64)` recursively splits at h=32, h=16, h=8,
producing 7 internal `gemm_axpy_into_view` calls and 8 calls to the scalar
`trsm_lower_base` at m=8. Even though each GEMM hits the fast path, the
scalar base case at m=8 with n_rhs=64 contributes ~7 µs/call × 8 calls =
~56 µs — about 70% of the 80 µs TRSM wall time. The scalar base case does
not vectorise because m=8 is below the GEMM threshold for any of its
internal updates.

Closing the TRSM gap requires either:
- A SIMD-aware `trsm_*_base` at m ≤ 8 (new kernel), or
- A raised `TRI_BASE_THRESHOLD` paired with a wider TRSM kernel
  (algorithmic change with non-trivial correctness implications).

Both are out of scope for the d36cc414 follow-up.

## § 6 — Recommended Branch and Amendments

**Recommendation: branch (b).** No in-scope fix exists. The 1.5-1.7× gap
at GF(251)/n=64 (and GF(251)/n=256 deficient invert) is structural at the
PLE-base / TRSM-base level and would require substantial new kernels to
close.

### Why no code change is landed by `d36cc414`

Per the §5 audit, the maximum savings from removing every identified
Rust-layer per-call overhead is ~2-3 µs at the op level — insufficient to
move any of the five cells across the 1.5× threshold. The remaining gap is
in the underlying PLE/TRSM kernels and algorithms, not in the
dispatch path. Implementing the kernel-level changes (SIMD trsm_base,
wider PLE kernel, or float-modular PLE) is each a multi-day effort
appropriate for a separate JIT issue, not a hotfix.
