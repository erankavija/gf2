## Traps — do not repeat these (NEW this session; s1–s6 traps still apply)

- **A handoff's "reviews PASS" may not include the FORMAL code-review gate.** Handoff-6 said C.1 was "merged + both reviews PASS" — those were the lead Tier2/3 + adversarial pre-reviews; the formal codex gate then failed THREE rounds with substantive findings (default-stream launches, racy stream binding, doc debt). Never count a task review-clean until `jit gate pass <id> code-review` has actually PASSED at the merged HEAD. Budget review rounds accordingly.
- **`HipStreamPool::acquire()` must NEVER be used for worker-stream binding.** Its atomic cursor advances in *call* order — under `into_par_iter` the interleaving is scheduler-dependent, so worker `i` is NOT guaranteed stream `i % n` and a recorded `stream_id` can describe a different stream than the one used (formal r2 F1). Use the indexed `HipStreamPool::get(i % len)` (landed `87c5e99e`). The pool docs now say this; do not regress them.
- **An overlap smoke test with ONE batch per worker measures nothing.** C.1's original 61.2% overlap passed only because device-wide sync stretched GPU intervals across other workers' prep; under real per-stream sync the same config measured 14.7%. The config must give every worker ≥2 batches so prep(N+1)∥decode(N) actually exists (landed config: 8 workers × 384 frames = 3 batches/worker → 100.0%). Any future overlap assertion must verify the double-buffer steady state is reachable.
- **Background workers can die at the provider session limit with NO report and NO commits.** The de160fc5 worker burned ~59 min, produced 15 files of uncommitted WIP, and its "result" was the limit notice. Lead countermeasures now standard: (a) snapshot-commit orphaned WIP on the worktree branch immediately (labeled UNVERIFIED); (b) treat such WIP as suspect — it includes edits the worker was told to avoid and has zero test evidence; (c) consider telling long-task workers to commit incrementally per deliverable.
- **The 5s fast tier flakes wholesale under external load — diagnose before assuming regression.** 10/10 tests of `ldpc_systematic_encoding` timed out at uniform ~5.3s under an external `cc1` build (loadavg 45–58); all pass on a quiet host. A whole-binary uniform timeout pattern = load, not code. Check `ps -eo pcpu,comm --sort=-pcpu` + loadavg BEFORE investigating test code.
- **A loadavg-quiet window can close mid-benchmark — bracket and disclose.** The first post-rework throughput run was contaminated (hybrid ±41.85); the fix: chain sustained-quiet check (two samples 60s apart) → immediate run → record loadavg before AND after in the receipt. CPU arms' variance is the canary (±0.0007 = clean window; the arms run in order CPU-1 → CPU-24 → hybrid, so late-arriving load hits the hybrid arm first... actually LAST — check which arm shows inflated σ to localize the contamination window).
- **Shell cwd persists across Bash calls (s-trap reaffirmed, nearly cost a mis-merge).** A `cd <worktree> && grep` left the shell IN the worktree; the subsequent `git merge` ran there and silently no-op'd ("Already up to date"). Always `cd` back to main (or use `git -C`) before any git state command; verify with `git log --oneline -1` that you're on the expected HEAD.
