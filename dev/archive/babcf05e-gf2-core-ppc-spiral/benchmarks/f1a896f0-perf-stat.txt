Fixed-iteration methodology:
  Criterion adapts iteration counts per function, so L1d rates from filtered
  Criterion binaries were not apples-to-apples per matvec. The rework adds
  crates/gf2-core/examples/sparse_block_csr_perfstat.rs, which constructs the
  same deterministic LDPC-like 8192x16384 row_weight=6 matrix, verifies
  block-CSR output against CSR once, then executes exactly 50,000 matvec calls.
  Each perf invocation below uses the same operation count and `perf stat -r 10`.

  perf stat -r 10 -e L1-dcache-loads,L1-dcache-load-misses

Tuning notes:
  Quick fixed-iteration timing across block_rows={16,32,64} did not show a
  useful wall-time difference for no-prefetch block CSR on this fixture:
    block_rows=16: 815.9 ms / 20,000 matvecs
    block_rows=32: 809.9 ms / 20,000 matvecs
    block_rows=64: 806.4 ms / 20,000 matvecs
    CSR:           694.4 ms / 20,000 matvecs
  Prefetch-distance quick timing at block_rows=32 and 20,000 matvecs:
    d=4:  1018.2 ms
    d=8:  1001.8 ms
    d=16: 1008.7 ms
    d=32: 1048.0 ms

Conclusion:
  The fixed-iteration harness removes Criterion's adaptive-iteration confounder.
  On the LDPC-sized 8192x16384_w6 fixture, block CSR does not satisfy the hard
  L1d miss-rate criterion versus existing CSR:
    CSR:                 2.61%
    block no-prefetch:   3.92%
    block prefetch d=16: 3.43%
  Absolute L1d misses per 50,000 matvecs are also slightly higher for block CSR
  than CSR in this fair fixed-iteration comparison. Prefetch lowers the block
  layout's miss rate versus no-prefetch, but wall time worsens. The rework
  therefore disables software prefetch in the default block-CSR `matvec()` and
  leaves prefetch available only through explicit `matvec_with_prefetch_distance`.
