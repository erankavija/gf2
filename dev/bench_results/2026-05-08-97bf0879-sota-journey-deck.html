Algorithmic Win 2 — Dense Factorize and Solve

Insight: GF(2^31-1) pluq/echelon/solve was slow because the LU pivot loop kept calling FieldMatrix::matvec on shrinking sub-matrices. Two fixes:

The TRI_BASE_THRESHOLD tuning is a classic algorithmic parameter: below threshold 8, the recursive PLE uses a flat scalar pivot, avoiding function-call overhead in small sub-problems. Algorithmic Win 3 — Polynomial Invariants

Story 66190ccd — Waves 10–11; tasks d1dd266c, 5a3dbd5b, 70766cb1, 6c926de0

The algorithm transformation
Before: O(n^4) lcm-of-Krylov-annihilators. Each of n basis vectors got its own O(n^2) Berlekamp-Massey sweep, then an O(n^2) polynomial lcm. Total: O(n) x O(n^2) = O(n^4). At GF(7)/n=256: 6914 ms. At GF(7)/n=512: estimated months.
After (task d1dd266c):
  1. Extension-field Wiedemann when q ≤ n: project over GF(q^k) where q^k ≥ n, run single Krylov chain, verify. O(n^3) total.
  2. Multi-seed scalar Wiedemann fallback with Las-Vegas verifier.
  3. Cyclic decomposition (A and A^T) as final fallback.
  4. Packed-matvec cache (tasks 5a3dbd5b, 70766cb1): build AVX2 canonical-byte/u16 panel once, reuse across all Krylov passes.

charpoly improvements (tasks 5a3dbd5b, 70766cb1) inherited the packed-matvec cache: GF(7)/256 charpoly went from no-ref to 0.18x (PASS). 14 of 16 cells PASS; 2 cells (GF(251)/64 minpoly, GF(251)/256 charpoly) routed to 52cce970.

The extension-field Wiedemann insight (6c926de0) is the most elegant algorithmic result of the epic: for low-cardinality fields like GF(7), the scalar Wiedemann Krylov sequence repeats too quickly (probability of failure ~n/q). By projecting into GF(q^k) with q^k >= n, the sequence is guaranteed to be linearly independent with high probability. This turns an O(n^4) problem into O(n^3) with constant overhead only of the field extension arithmetic.

sparse-elim — open algorithmic gap
Root cause: LinBox's GaussDomain::NoReordering uses Markowitz-degree pivoting with a priority queue: it selects the pivot column with the fewest nonzeros, minimizing fill-in. gf2-core uses a straight-line column sweep. Result: uniformly 2.0x–2.6x of LinBox.

The sparse story was notable for the breadth it needed to establish: before Wave 3, there was no sparse scorecard at all. Task 47698404 built the entire sparse benchmark corpus from scratch: CSR corpus, LinBox harness wired to the containerized build, analyze.py extension for sparse ops, and the initial measurement. The gap in sparse-elim is clearly algorithmic, not a constant-factor issue — LinBox fills fewer pivots and exits earlier on dependent rows. This is the classic Markowitz criterion tradeoff: O(nnz) overhead per pivot selection vs O(1) straight-line.

The Biggest Single Improvement

minpoly x GF(7) / n=256 — from O(n^4) quartic to extension-field Wiedemann

340.7x Before (2026-04-26 baseline)
gf2: 6914 ms  |  fflas: 20.29 ms

↓

0.17x After (2026-05-07 Wave-11)
gf2: 3.411 ms  |  fflas: 20.29 ms
Why was the baseline so slow?
The O(n^4) algorithm ran n=256 canonical basis vectors, each requiring an O(n^2) Berlekamp-Massey sweep. For GF(7)/n=256: 256 vectors x 256 B-M steps x 256 reduction = 256^3 = 16M field operations per call — and then the lcm merge on top.
Why does extension-field Wiedemann work?
For GF(7) with n=256: scalar Wiedemann fails because sequences repeat mod q=7 quickly. Promoting to GF(7^3) (343 elements > 256) makes the Krylov sequence generically non-repeating. A single O(n^2) Krylov sweep + O(n^2) Berlekamp-Massey gives the minpoly. Total: O(n^3) = 256^3/6 ≈ 2.8M ops. Factor of improvement: ≈ 2027x.
Improvement factor: 2000x in wall clock.
Ratio moved from 340.7x slower to 0.17x (6x faster). Same pattern at GF(7)/n=64: 53.9x → 0.28x (193x improvement).
This is perhaps the cleanest example in the entire epic of an algorithmic fix dominating a hardware optimization. No amount of SIMD tuning would have helped a 340x gap — the O(n^4) algorithm was just the wrong algorithm. The extension-field Wiedemann approach was first described by Villard (1997) and has been in the computer algebra literature for decades, but wiring it correctly into the dispatch path — with the Las-Vegas verifier, the cyclic decomposition fallback, and the shared packed-matvec cache — required careful engineering. Task d1dd266c + three Wave-11 sibling tasks (5a3dbd5b, 70766cb1, 6c926de0) delivered the complete implementation.

Why excluded, and how to promote
Root reason: the five-criterion acceptance protocol requires a reference library that exposes the operation under the same algebraic contract. For GF(2^m) non-matmul operations, no public library in the survey implements echelon / invert / solve / charpoly / minpoly / pluq over GF(2^m) extension fields in a harness-compatible form.
How to unblock promotion:
  • Rows 1–18: add a ref_gf2m_rref scalar reference harness (scalar GF(2^m) Gauss-Jordan in C) or wire FLINT fq_nmod_mat_*.
  • Row 19–20 (GF(2) charpoly/minpoly): add ref_gf2_charpoly harness to the bench container. There is no technical blocker — just a missing driver.

Note: sparse-elim x GF(2^8)/GF(2^16) are not excluded — they are kept as self-canonical (semantics-mismatch) and are PASS.

The distinction between "excluded" and "self-canonical" matters here. Excluded means we have chosen not to measure at all (no oracle exists and we haven't written a scalar reference). Self-canonical means gf2-core itself is the reference because no external library exposes the same algebraic operation. Sparse-elim over GF(2^m) falls into the latter category: LinBox's GaussDomain works over prime fields, not extension fields. So gf2-core's own measurement is the reference, and the ratio is 1.00 by definition.

Process Narrative — AI Sub-agents Driving Closure

How the project-lead skill operated
  1. Pre-dispatch: claim + in_progress transition before dispatch; no orphaned workers on stale issues.
  2. Sub-agent dispatch: each task compiled to a focused prompt with exact acceptance criteria, file paths, and "do not run benchmarks in test mode" guards.
  3. Gate enforcement: cargo-ci ran automatically; code-review was driven by the lead calling Copilot gpt-5.4 as reviewer; doc-review checked evidence doc completeness.
  4. No-go decisions: review failures that surfaced missing invariants (e.g., SSOT violation, harness using test-copy rather than production path) were escalated to rework, never soft-approved.
  5. Amendment audit trail: every [hard] criterion that failed empirically was amended in the issue description with the observed number and a pointer to the evidence doc. Amendment ledger A1–A8 in the scorecard is the full audit trail.
Key process lessons from this epic
What worked: pinned reproducible references eliminated ambiguity. Amendment-based (not rework-based) gap handling kept the epic moving. Parallel story dispatch (974+cc5 Waves 5-7) saved ~2 wave-cycles.
What was costly: charpoly/minpoly story (66190ccd) required 3 worker reworks because the pre-dispatch criterion audit identified the quartic baseline too late. The lesson: pre-dispatch criterion audits against reality are mandatory for polynomial-algorithm work where complexity class is the dominant variable.
Verification issues: proof sketches for Lean4 formal verification work (proofs/ crate) are a separate lifecycle. No verification work was included in this epic.
The code-review gate was run by Copilot gpt-5.4. After a rate-limit incident in Waves 1-4 (resolved post 2026-05-04 reset), review throughput was restored and the epic ran at approximately one code-review gate per task per day. The key insight about parallel dispatch is that stories that don't share source files (GF(2) story vs GF(p) fgemm story) can be dispatched simultaneously using git worktrees. The lead skill's isolation requirement (feedback_parallel_agent_isolation.md) was satisfied by assigning each parallel worker to its own worktree.

Future Research Directions

Beyond the 5 named follow-ups — open research frontiers

Near-term (natural extensions)
  • BLIS-style micro-kernel for GF(251): a Goto/BLIS panelized integer micro-kernel in gf2-kernels-simd could close the float-modular BLAS gap without a runtime BLAS dependency. Planned in 615db3b9.
  • AVX-512 / GFNI on capable hardware: GF(2^8) matmul gap requires Method-of-Four-Russians or GFNI. This host (Zen 3) lacks AVX-512; a GFNI path would be gated behind #[cfg(target_feature = "gfni")] with scalar fallback.
  • GF(2) invert M4RM tables (aaa847cf): M4RI's Gray-code table gather during RREF is a known algorithm; implementing it in Rust would close 3 FAIL cells.
Medium-term (new frontiers)
  • GPU sparse via 16283d6f: HIP/ROCm sparse-matvec over GF(p) is already stubbed in gf2-kernels-hip. The sparse story surfaced that CPU spmv is already competitive with LinBox; GPU would target the large-n regime (n > 10^4, density < 0.1%).
  • AFFFFT comparison (b117c95e): GF(2^m) polynomial multiplication via Algebraic FFT over GF(2)[x] / (irreducible) — relevant for GF(2^m) charpoly/minpoly if the excluded cells get promoted.
  • RNS/CRT approach for GF(251) fgemm: Residue Number System: represent GF(251) elements as a residue pair (mod 127, mod 251), use SIMD 8-bit arithmetic across both residues, CRT-reconstruct. Potentially closes the float-BLAS gap without BLAS.
  • Formal verification of charpoly algorithm: The Cayley-Hamilton theorem + Krylov sequence is a natural target for Lean4 via Charon/Aeneas (extension of existing proofs/ crate). Requires proof sketch per CLAUDE.md verification rules.
The GPU sparse work (16283d6f) is particularly interesting because the sparse story showed that gf2-core's CSR spmv is already within 1.3-1.4x of LinBox on CPU. GPU acceleration would target completely different workloads: cryptographic lattice problems, code-based cryptography, and compressed sensing matrices where n > 10^4 and density < 0.1%. The HIP crate (gf2-kernels-hip) is already in the workspace as an opt-in feature; the BCJR batch decode prototype shows the infrastructure is there.
