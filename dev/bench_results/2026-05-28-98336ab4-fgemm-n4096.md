### 2.2 Gop/s extraction

All per-trial Gop/s values are extracted from the criterion display median (the middle value from `time: [low median high]`), not from `estimates.json` snapshots. The snapshot mechanism has a known timing race: `estimates.json` is overwritten by criterion after the display output, so the file may show the previous trial's data when polled immediately after the log line appears. Log-based extraction gives the authoritative per-trial measurement.

Formula: `Gop/s = 2 * n^3 / median_ns` (one GEMM = 2*n^3 multiply-add pairs).

### 4.4 Why the consolidated n=4096 sweep showed a spurious GF(7)/256 = 44.3

The consolidated 6-prime n=4096 driver (§2) used a filter starting at **n=256** (`(256|1024|4096)$`), with no n=64 cell to warm the small-prime Candidate-C instruction cache first. GF(7)/256 therefore hit a **cold i-cache** and read 44.3 Gop/s — a −37% artifact of the measurement filter, not a code change. The `41096af5` baseline filter included n=64, so its 70.7 reading is warm. Matching the baseline's warmup ordering (this §4 run) returns GF(7)/256 to 72.34 Gop/s (+2.25% vs baseline). The mechanism is corroborated by the fact that only n=256 cells (first-touch after the n=64-less filter start) were affected in the consolidated run, while n=1024 cells (which follow n=256 and are thus warm) were flat.

## 5. GF(251)/4096 — apples-to-apples PASS (isolated re-measurement)

### 5.1 Verdict

| measurement | gf2 5-trial median | wall ratio (fflas/gf2) | verdict |
|---|---:|---:|---:|
| consolidated 6-prime sweep | 104.68 Gop/s | 1.519x | sweep L3-contention artifact |
| **isolated single-prime (authoritative)** | **106.71 Gop/s** | **1.490x** | **PASS** |
| 74ba1cdc R1 isolated (prior session, corroboration) | 108.42 Gop/s | 1.466x | PASS |

The threshold is wall ≤ 1.5x. The isolated re-measurement (this session, same protocol) gives **1.490x — PASS**, corroborated by 74ba1cdc R1's independent isolated 1.466x.

### 5.2 Why the isolated number is the fair comparison

The fflas reference (158.964 Gop/s for GF(251)/n=4096, from `2026-04-26-reference.csv`) was produced by fflas-ffpack run **one configuration per process** — i.e. in isolation, with no other n=4096 GEMM having polluted the L3 before it. To compare like-for-like, gf2 must be measured under the same isolation condition. The consolidated sweep instead runs GF(251) **5th**, after GF(7), GF(31), GF(127), and GF(241) have each executed an n=4096 GEMM in the same process. That is gf2-contaminated vs fflas-isolated — apples-to-oranges.

### 5.3 The L3 mechanism

GF(251)/n=4096 dispatches to **Route A** (`select_f32_path`: `P == 251 && n >= 512`), a packed-f32 AVX2 Barrett kernel whose blocking schedule was tuned by 74ba1cdc to assume ~16 MB of free L3 (the Zen 3 CCX1 L3 size) for keeping the A/B panels warm. In the consolidated sweep, the 5 preceding n=4096 GEMMs (each operand matrix is 4096·4096·4 B = 64 MB in f32, far exceeding L3) leave their tail data resident in L3, so Route A enters with its panel-budget assumption already violated and pays extra DRAM traffic.

This mechanism is **specific to Route A's L3-budget heuristic**. The signature in the consolidated data confirms it: the five non-Route-A primes (GF(7)/31/127 via small-prime scalar; GF(241) via Route A but with a larger fflas headroom; GF(65521) via the f64 cascade) were flat-or-better in the sweep, and **only the L3-sensitive Route A cell dropped**. A cold-start L3 effect of the same family was previously documented for GF(7)/256 in the prior benchmark session.

### 5.4 Isolated re-measurement protocol

5-trial CCX1-pinned bench of **only** GF(251)/n=4096 (filter `gemm/Fp_251/Fp_251/4096$`, so no other prime runs first in the process), `taskset -c 6-11 nice -n -5` (nice denied as non-root; pinning effective), quiet-host check before each trial, `median_ns` read from `target/criterion/gemm_Fp_251/Fp_251/4096/new/estimates.json` (snapshotted per trial), `Gop/s = 2·4096³ / median_ns`.

## 6. Code changes

### 6.1 Bench harness (crates/gf2-core/benches/fieldmatrix_gemm.rs)

Added constant `SQUARE_SIZES_SMALL_PRIME_N64_TO_4096 = &[64, 256, 1024, 4096]` replacing the per-prime `SQUARE_SIZES_SMALL_PRIME_WITH_N64 = &[64, 256, 1024]` for GF(127) and GF(241). Updated `bench_gemm_fp_127` and `bench_gemm_fp_241` to use the new constant. This is the harness gap that caused GF(127)/4096 and GF(241)/4096 to be absent from prior bench sweeps.

### 6.2 Proptest (crates/gf2-core/tests/route_a_gf251_production_dispatch_proptests.rs)

Added `proptest_production_dispatch_n4096_matches_scalar` which uses a rectangular shape (m=4, k=16, n=4096) to verify that the production `select_f32_path`-dispatched GF(251)/n=4096 GEMM matches the scalar oracle. This bounds oracle runtime to 4*16*4096 ≈ 262K ops while exercising the full Route A branch. **PASSES** in CI (4025 tests total, 0 failures).

### 6.3 No dispatch changes

No changes to `select_f32_path`, `select_f64_path`, or any kernel. Route A and f64 cascade are unchanged from the `74ba1cdc`/`0749dbad` landings.
