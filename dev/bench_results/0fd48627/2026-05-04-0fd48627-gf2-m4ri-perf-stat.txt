 Notes:
   * 5.6 IPC is at or just below the Zen 3 4-wide retirement port
     budget once 64-bit-ALU XOR throughput limits and the DSB µop-cache
     hit rate are factored in. This is consistent with a kernel that
     does NOT spill to memory between Gray-code-table accumulator
     updates — i.e. the M4RM hot path is broadly compute-bound at this
     size, not memory-stalled.
   * Frontend stalls: 0.00 % of cycles. The DSB / decode pipeline is
     not the bottleneck.
   * dTLB-load-misses is below 14 K across 300 multiplies = ~46
     misses per multiply. With 4 KiB pages this is consistent with
     each multiply's working set fitting inside the dTLB reach
     (Zen 3 L1 dTLB = 64 entries × 4 KiB = 256 KiB; L2 dTLB = 2048
     entries). The full n=1024 working set (~384 KiB across A, B, C
     plus a 64 KiB Gray table) overflows L1 dTLB but fits in L2 dTLB
     by 5x — explaining why dTLB pressure is negligible.

     7,026,789,243      cycles:u                          ( +-  0.51% )
    25,431,073,507      instructions:u                    ( +-  0.00% )
     1,349,369,390      l2_cache_accesses_from_dc_misses:u ( +-  0.20% )
         9,231,568      l2_cache_misses_from_dc_misses:u  ( +-  8.11% )

       1.473703128 +- 0.009126652 seconds time elapsed    ( +-  0.62% )

 Derivation:
   L2-from-DC accesses                    = 1349 M
   L2-from-DC misses (i.e. miss to L3+)   =    9 M
   L2 hit rate on demand DC misses        = 99.3 %

   The working set at n=4096 is ~6 MB (3 matrices × 2 MB) plus the
   1024-entry Gray-code panel (~32 KB) — that overflows the per-core
   L2 (512 KiB) but fits comfortably in the shared L3 (32 MiB per CCX
   × 2 = 64 MiB total). The 99.3 % L2 hit rate is paradoxical against
   a 6 MB working set; the explanation is that the M4RM tile schedule
   (`use_register_tiled_schedule()` + `multiply_register_tiled()`)
   confines the inner-loop access pattern to the active panel + tile,
   not the whole working set. DRAM demand:
       ~ 9 M × 64 B / 1.43 s = 403 MB/s  (~ 0.8 % of DDR4-3200 peak).

   Even at n=4096, the kernel is **not DRAM-bandwidth-bound**.

============================================================
 Methodology notes
============================================================

  * Frequency boost / governor: host defaults left on (matches the
    2026-04-26 baseline idiom; the host.txt records governor at
    capture time). Effective cycles_frequency ≈ 4.6 GHz at n=1024,
    ≈ 4.7 GHz at n=4096 — same boost regime.
  * SMT: on (host default). The profiling binary is single-threaded.
  * Coverage % reflects PMU multiplexing across nine concurrently
    requested events; the counter values are time-scaled by perf.
  * The example binary is the production-path
    `gf2_core::alg::m4rm::multiply` — same call site exercised by
    the strassen-crossover benchmark. The harness adds a fixed
    warmup loop and an output-checksum XOR; both contribute < 0.5 %
    of cycles.
