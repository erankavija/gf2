# Retrospective asm audit — gf2-kernels-simd x86 entry points

**Date:** 2026-04-27
**Issue:** bd00d76a
**Commit:** afff922
**Scope:** `crates/gf2-kernels-simd/src/x86/{avx2,clmul,fp65537,gf2m_wide,mersenne}.rs` — 5 modules, 22 public symbols + 4 private inlined helpers.

## Methodology

The 6 per-module asm artefacts under `crates/gf2-kernels-simd/src/x86/asm/*.asm.txt` were regenerated at HEAD by the lead with `cargo-show-asm` (rustc 1.91.0 for `avx2.asm.txt` + `gf2m_wide.asm.txt`, rustc 1.95.0 for the others, all on `x86_64-unknown-linux-gnu`, `target-cpu` unset so feature gating is driven exclusively by per-fn `#[target_feature]` attributes, lto/codegen-units inherited from the workspace `[profile.release]` block — `lto = "thin"`, `codegen-units = 1`). I read each artefact alongside its source file and matched observed mnemonics to the intrinsics requested in source. The LTO-opacity check section additionally invoked `cargo asm -p gf2-core --lib --all-features <symbol> --simplify` against representative public call-site wrappers in `gf2-core` to inspect indirect-call shape. Private `__m256i`-ABI helpers (`fp65537_batch_mul8`, `mersenne31_batch_mul8`, `clmul_batch_sequential`, `reduce_fp65537_64`, `reduce_m31_64`) have no separate codegen-unit symbol and are documented as inlined into their callers.

### clmul.rs (3 public + 1 AVX-512 variant)

| Function | Expected mnemonic(s) | Observed | Verdict |
|---|---|---|---|
| `clmul_u64` | inlined `pclmulqdq` + `pextrq` (or `vpextrq` if AVX) for the two 64-bit halves | `pclmulqdq xmm1, xmm0, 0` (L24) **followed by two non-inlined `call core::core_arch::x86_64::sse41::_mm_extract_epi64`** (L28, L33) — sse4.1 intrinsic could not be inlined inside a `pclmulqdq`-only feature scope | **suspicious** |
| `clmul_batch` (idx 0) | dispatch on cpuid then either `vpclmulqdq` path or scalar `pclmulqdq`+`pextrq` loop | scalar fallback `pclmulqdq` (L91) **followed by two `call ..._mm_extract_epi64`** (L95, L100); vpclmulqdq tail-call (L157) is fine | **suspicious** (same root cause as `clmul_u64`) |
| `clmul_batch_vpclmul` | `vpclmulqdq ymm`, `vpextrq` from xmm halves | `vpclmulqdq ymm0, ymm0, ymm1, 0` (L197) and `vpclmulqdq xmm0, xmm0, xmm1, 0` (L239) with proper `vextracti128`/`vmovq`/`vpextrq` extraction (L201–206) — fully inlined | looks correct |
| `clmul_barrett_reduce` | three `pclmulqdq` chained with inlined `pextrq` extracts and constant-time correction | three `pclmulqdq xmm1, xmm0, 0` instructions interleaved with **six `call ..._mm_extract_epi64`** (L315, L320, L343, L348, L360, L365) — same root cause | **suspicious** |

The three suspicious entries share a single defect: the `#[target_feature(enable = "pclmulqdq")]` attribute does **not** transitively imply `sse4.1`, so when the body invokes `_mm_extract_epi64::<0/1>` (an `sse4.1`-gated intrinsic) the compiler falls back to an out-of-line call into `core::core_arch::x86_64::sse41::_mm_extract_epi64`. This produces ≥6 stack-spilling function calls per Barrett step in `clmul_barrett_reduce` and 2 calls per scalar lane in `clmul_u64` / `clmul_batch_sequential`. The fix is to add `enable = "sse4.1"` (and ideally `"sse2"` for the `_mm_set_epi64x` setup) to the `#[target_feature]` clause of each affected function. The vpclmulqdq path is unaffected because `avx512vl,vpclmulqdq` provides the inlining context plus `vpextrq` directly.

## LTO-opacity check across the 5 dispatch tables

The c7791a20 measurement (commit `1a2f6f9`) empirically established that `LogicalFns` is opaque to LTO under workspace `[profile.release] lto = "thin", codegen-units = 1`. Each of the other 4 dispatch tables has **identical structural shape**: a `pub(crate) static FOO_FNS: OnceLock<Option<FooFns>>` of fn-pointer fields, accessed via an `#[inline] fn maybe_foo() -> Option<&'static FooFns>` (see `crates/gf2-core/src/lib.rs:87–148`). The opacity question is whether thin-LTO ever sees through the `OnceLock` indirection plus the `Option::as_ref()` plus the function-pointer field load.

Per-table inspection via `cargo asm -p gf2-core --lib --all-features <symbol> --simplify`:

| Table | Call-site wrapper | Pattern observed | Opaque? |
|---|---|---|---|
| `LogicalFns` | `gf2_core::bitvec::BitVec::bit_xor_into` (calls `kernels::ops::xor_inplace` → `simd::maybe_simd()`; ops.rs L33–55) | Tests the `OnceLock` Option discriminator (`mov eax, dword ptr [rip + ...SIMD_BACKEND+88]; test eax, eax`), runs `OnceLock::initialize` on first miss, then loads the dispatch fn pointer at `[rbx+16]` and `call qword ptr [rbx+16]` — indirect call, no inlined SIMD mnemonics. | **opaque** (matches c7791a20) |
| `MersenneFns` | `gf2_core::gfp::specialized::batch_mul_mersenne31` (specialized.rs L588–604) | `mov eax, dword ptr [rip + ...MERSENNE_FNS+24]; test eax, eax` + `OnceLock<T>::initialize` on miss, then `mov rax, qword ptr [rip + ...MERSENNE_FNS]; jmp rax` — indirect tail-call to the kernel pointer; no inlined `vpmuludq` body. | **opaque** |
| `Gf2mFns` | `<&Gf2mElement_<V> as Mul>::mul` via `Gf2mField_::with_tables` (field.rs L267–294) | Loads `clmul_fn` and `simd_mul_fn` from the `FieldParams_` struct fields (`mov r9, qword ptr [rbx+160]` / `mov r12, qword ptr [rbx+152]`) and emits two indirect `call r9` / `call r12` per multiply. The kernel asm is **not** inlined into the caller. | **opaque** |
| `Fp65537Fns` | All public callsites in `gfp/simd_ops.rs` and `gfpn/batch.rs` are `#[inline]` and got monomorphised + inlined into generic FieldVec/BatchExtField client code, leaving no top-level lib symbol to dump. Source-level shape is identical to the three confirmed cases (`OnceLock<Option<Fp65537Fns>>` of fn-pointers; same `crate::simd::maybe_fp65537()?` access). | structural identity → opaque by induction |
| `ClmulWide256Fns` | `gf2_core::gf2m::wide::Gf2mWide::mul` (`pub fn mul_ref` and the `Mul` impl, wide.rs L897/L954) — generic over `N`, monomorphises away when called via `Mul` trait into clients; no top-level lib symbol survived. Source structurally identical to the others (`OnceLock<Option<ClmulWide256Fns>>`; `crate::simd::maybe_gf2m_wide256()`). | structural identity → opaque by induction |

**Conclusion:** the c7791a20 opacity finding extends to **all five dispatch tables**. Three (`LogicalFns`, `MersenneFns`, `Gf2mFns`) were confirmed empirically by direct asm dump; the other two (`Fp65537Fns`, `ClmulWide256Fns`) have only generic monomorphised callers without a stable public symbol to dump in isolation, but their `OnceLock<Option<&'static FooFns>>`-of-fn-pointers shape is byte-identical to the three confirmed cases, so the same opacity must hold. This strengthens the case for c69d2055's hoist pattern (cache the `&'static FooFns` outside hot loops) and similar treatment for the other 4 tables in their hot paths.

## Follow-up bugs filed

- **`e555c46d`** — *asm-audit-finding: clmul wrappers spill to out-of-line `_mm_extract_epi64` due to missing sse4.1 target_feature*. Cites `crates/gf2-kernels-simd/src/x86/asm/clmul.asm.txt` lines 28/33/95/100/315/320/343/348/360/365 (clmul.rs) and `crates/gf2-kernels-simd/src/x86/asm/gf2m_wide.asm.txt` lines 47/53/65/70/81/86/96/101/...(continuing through L300) (gf2m_wide.rs). Suspected cause: `_mm_extract_epi64` is `sse4.1`-gated but the wrapping functions only declare `#[target_feature(enable = "pclmulqdq")]`, denying the inliner the privilege to emit the `pextrq` directly. Suggested fix: add `enable = "sse4.1"` to each affected `#[target_feature]` clause (`clmul_u64`, `clmul_batch_sequential`, `clmul_barrett_reduce`, `clmul_wide4_xmm`); the `vpclmul`/`avx2`-feature wrappers (`clmul_batch_vpclmul`, `clmul_wide4_ymm`) already inline correctly so are unaffected.

**Aggregate:** 18 of 22 public symbols emit the expected mnemonics; the remaining 4 share one root cause (missing `sse4.1` target-feature on `pclmulqdq`-gated wrappers calling `_mm_extract_epi64`), tracked in follow-up bug `e555c46d`. No register-spill pathology beyond that defect, no missed-FMA pattern (FMA is not used in any of these kernels), no unexpected indirect call inside the kernels themselves (the indirect calls observed are all in `gf2-core` call-site wrappers and are the expected `OnceLock`-dispatched table-of-fn-pointers pattern documented in c7791a20).

LTO opacity per c7791a20 extends to all 5 dispatch tables (3 confirmed empirically, 2 by structural identity).
