## Family classification

The five primes split into four families against fflas-ffpack 2.5.0
behaviour. Families are defined by the underlying fflas-ffpack
representation (which determines the BLAS/scalar path the reference takes)
and by the gf2-core kernel path (Goldilocks/Mersenne/Solinas delayed
reduction; see `2598b981` § *Within-10× result*).

| family | members | fflas-ffpack representation | gf2-core kernel path | bit-width |
|---|---|---|---|---|
| **Tiny prime** (`p ≤ 31`) | GF(7), GF(31) | `Givaro::Modular<int64_t>` (per `fflas_bench.cpp` line 922-928 for GF(7); GF(31) inherits the same path) | delayed-reduction Goldilocks/Solinas (`e7ab802d`) | 3-5 bit |
| **Word-fits-in-byte** (`32 ≤ p < 256`) | GF(251) | `Givaro::Modular<float>` (per `fflas_bench.cpp` line 912-919) — float-modular fast path with cardinality ≤ 251 | delayed-reduction Goldilocks/Solinas (`e7ab802d`) | 8 bit |
| **Word-fits-in-u16** (`256 ≤ p < 2^16`) | GF(65521) | `Givaro::Modular<int64_t>` (per `fflas_bench.cpp` line 903-909); largest u16 prime in the corpus | delayed-reduction Goldilocks/Solinas (`e7ab802d`) | 16 bit |
| **Mersenne fast path** (`p = 2^k − 1`) | Mersenne31 (`2^31 − 1`) | `Givaro::Modular<int64_t>` over a 31-bit modulus (per `fflas_bench.cpp` line 894-901); fflas does NOT use a Mersenne-aware reduction | delayed-reduction with Mersenne-aware bit-trick reduction (`e7ab802d`) — gf2-core IS Mersenne-aware | 31 bit |

Note that the **fflas-ffpack reduction strategy** differs across families
(int64-modular vs float-modular vs int64-modular-31bit) but the
**gf2-core kernel** is uniform across all four families: the `e7ab802d`
delayed-reduction path delivers ≈ 3.7 Gop/s independent of prime size or
representation. This uniformity is precisely what makes the per-family gap
diagnostic — fflas-ffpack's family-specific kernels reveal where gf2-core
is missing comparable specialisation.

## Per-family verdict

Verdict tags follow the issue spec: `WITHIN_1.5X`, `NEEDS_NEW_KERNEL`, or
`EXCLUDED`. Cited ratios are gf2-core / fflas-ffpack at the headline
n=256³ uniform cell.

### Tiny prime (`p ≤ 31`) — GF(7), GF(31)

**Verdict: `NEEDS_NEW_KERNEL`** — gap factor at GF(7) is **13.7×**
(0.073× ratio inverse) at 256³ and **25.0×** (0.040× ratio inverse) at
1024³. fflas-ffpack runs a small-prime `Modular<int64_t>` path that, paired
with the openblas double-precision GEMM cascade, achieves 50–96 Gop/s for
GF(7); the same path applies to GF(31) (no representation change is needed
inside the `int64_t` instantiation for `p ≤ 31`). gf2-core's
delayed-reduction kernel is prime-agnostic above the kernel level and
delivers ~3.7 Gop/s flat, so the gap is intrinsic — there is no per-prime
fflas amplification we are paying for here, only a fundamentally different
kernel architecture (BLAS-cascade vs schoolbook-with-delayed-reduce).

**Candidate fix surface for `cc5de315` Wave 6 / design issue `5cacaec5`:**
small-prime packed kernel — at p=7 the field elements fit in 3 bits, so a
SIMD register packs 64–256 elements per lane. The likely architecture is
a packed-byte-MAC kernel that converts to int16/int32 for accumulation
before reducing. fflas-ffpack's `Modular<float>` GF(251) path provides an
order-of-magnitude blueprint via the BLAS3 cascade — at GF(251) fflas
hits **128.480 Gop/s** at 256³ with the float-modular trick, which is the
target gf2-core can plausibly approach for the entire `p ≤ 251` range with
a packed kernel. The crossover decision (where the packed kernel beats
delayed-reduction) is implementation-dependent but the GF(7)/GF(251) ratio
homogeneity (both at 3.7 Gop/s gf2-core) strongly suggests a single
`p ≤ 251` packed kernel handles both members of the small-prime spectrum
plus the byte family below.

**Note on GF(31) gap factor.** The expected GF(31) ratio sits between GF(7)
(0.073× at 256³) and GF(251) (0.029× at 256³); both endpoints use
related-but-distinct fflas paths (int64-modular for GF(7), float-modular
for GF(251)). GF(31) inherits int64-modular, so its gap factor is
expected to be **≥ GF(7)'s 13.7×** but **≤ GF(251)'s 35×**. The exact
number waits on the fresh pinned run flagged above; it does not change
the family verdict.

### Word-fits-in-byte (`32 ≤ p < 256`) — GF(251)

**Verdict: `NEEDS_NEW_KERNEL`** — gap factor at GF(251) is **34.7×**
(0.029× inverse) at 256³ and **36.0×** (0.028× inverse) at 1024³. This is
the **largest fflas-ffpack absolute throughput** among all measured GF(p)
cells (128.480 Gop/s at 256³). The float-modular path with cardinality
≤ 251 is the canonical "small-prime BLAS3" trick — fflas casts to single-
precision float for the multiplication, accumulates in double, reduces at
the panel boundary. Without that trick gf2-core's 3.7 Gop/s is
competitive in absolute terms with the **int64** path, but the
**float-modular** path is the operative reference here. The gap signature
is identical at 256³ and 1024³, so no Strassen-crossover dynamic is
operating; the gap is pure kernel architecture.

**Candidate fix surface for `cc5de315` Wave 6:** float-modular cascade or
packed-byte-MAC — see Tiny-prime verdict above. A single `p ≤ 251`
packed-byte kernel covering both Tiny and Byte families is the natural
unit of work; alternatively, a float-modular cascade matching fflas's
trick. Either way, the design issue `5cacaec5` should treat
`{Tiny, Byte} = {p ≤ 251}` as a single design unit, not two separate
kernels — the data shows the gap is the same family-level architectural
deficit.

### Word-fits-in-u16 (`256 ≤ p < 2^16`) — GF(65521)

**Verdict: `NEEDS_NEW_KERNEL`** — gap factor at GF(65521) is **8.5×**
(0.117× inverse) at 256³ and **11.3×** (0.089× inverse) at 1024³. This is
the **smallest gap** among the small/medium-prime families. fflas-ffpack
runs the `Modular<int64_t>` path here without the float-modular trick
(p > 251 cardinality), and openblas's BLAS3 still helps but less
amplification than the float-modular path. gf2-core's 3.7 Gop/s
delayed-reduction kernel here is closer-to-competitive than for the
smaller primes; the 256³ cell is just inside 10× per the
`2598b981` § *Within-10× result* check.

**Candidate fix surface for `cc5de315` Wave 6:** u16-packed kernel (4–8
elements per AVX2 lane after splitting hi/lo and reducing). The gap
factor (8–11×) is approachable with a SIMD-packed integer multiply path
that defers reduction across panels. This family is the **most likely
candidate for a near-term fix** because the gap is small enough that a
single PPC-style optimisation cycle can plausibly close it, whereas
small-prime requires a full kernel re-architecture. The design issue
`5cacaec5` should distinguish the u16 fix surface from the small-prime
fix surface — they are technically related (packed integer multiply) but
operate in different lane widths.

### Mersenne fast path (`p = 2^k − 1`) — Mersenne31

**Verdict: `WITHIN_1.5X`** (and in fact gf2-core is **ahead**) — ratio
gf2/fflas is **1.739×** at 256³ and **1.633×** at 1024³ (gf2-core
faster). gf2-core's Mersenne-aware reduction is more efficient than
fflas-ffpack's prime-agnostic `Modular<int64_t>` path on a 31-bit
Mersenne. This is the **only family where no new kernel is needed for
SOTA parity**. The PPC-era delayed-reduction landing (`e7ab802d`)
already covers Mersenne31 in the same uniform 3.7 Gop/s budget; fflas
runs at 2.13 Gop/s here because the int64-modular path doesn't
specialise the Mersenne reduction, while gf2-core does (per
`crates/gf2-core/src/gfp/montgomery.rs` and the Mersenne fast-path
documented in `CLAUDE.md` § Architecture).

**Implication for `cc5de315` Wave 6:** Mersenne31 should be treated as
the **negative-control reference** for the new kernels — any new
small-prime / byte / u16 packed kernel must not regress the Mersenne
case below the existing 3.7 Gop/s baseline. There is no fix surface
here; the design doc should not propose one.

## Implications for Wave 6

Hand-off summary for design issue `5cacaec5` and downstream implementation
issues `662f7a15` / `9e12659b` / `3d06224c`:

1. **Three families need new kernels**, not one. The naive read of
   `2598b981` ("gf2-core is ~3.7 Gop/s for all primes; fflas is faster
   on small primes") under-counts the diagnostic resolution: the Tiny+Byte
   pair benefits from a single packed-byte kernel, while u16 needs a
   distinct SIMD path. Treat them as **two design tracks**, not three.
2. **Mersenne is the negative control.** Any new kernel must not regress
   the Mersenne31 cell below the existing 3.7 Gop/s gf2-core baseline (or
   1.739× of fflas). A regression here would mean the new kernel's
   dispatch overhead is larger than the Mersenne fast-path's saving.
3. **The headline cell is `n = 256³`.** The 1024³ ratios are within
   ~10–25% of the 256³ ratios on every prime — the design doc should
   pick 256³ as the pivot cell and 1024³ as the regression check, not
   try to optimise both jointly.
4. **GF(31) measurement — closed 2026-05-04.** The follow-up pinned run
   was executed lead-direct after the Wave-3 worktree set tore down. The
   measured GF(31) gap factor (13.6× at 256³) tracks GF(7)'s 13.7× to
   within 1%, fully confirming the family-bracketing argument and
   closing the criterion-#1 measurement gap. No outstanding GF(31)
   action remains.
5. **The design doc must NOT make architectural decisions.** This
   evidence document hands off **per-family gap data only**. The design
   doc owns kernel selection (packed-byte vs float-modular cascade vs
   SIMD-u16), crossover thresholds, and dispatch wiring; this evidence
   document does not pre-empt those choices.
