## Change measured

The production `m4rm::multiply` path now:

1. selects wider Gray-code panels for the target row widths while keeping rows
   below the register-tiled width threshold on the historical schedule:
   - `n=1024`: 64 KiB table budget, `k<=9` (selects `k=9`);
   - `n=2048`: 128 KiB table budget, `k<=9` (selects `k=9`);
   - `n=4096`: 256 KiB table budget, `k<=9` (selects `k=9`);
2. removes the previous next-panel prebuild/prefetch path from production.
   Same-session timings showed the two-table schedule evicted useful
   current-panel data on the target 2048/4096 rows. Production now updates from
   one Gray table at a time.

The implementation remains behind the existing safe `BitMatrix` / `m4rm::multiply`
APIs. The benchmark harness now reports `production_auto` separately from
`legacy_64k_max8`.

## Criterion results

Times are Criterion middle estimates. Throughput uses the same `2*n^3` bit-op
normalizer used by the predecessor M4RM notes, so ratios are comparable to the
M4RI reference throughput.

### Same-session before/after production comparison

The pre-change rows were collected before editing production policy in this
session with the old production `64 KiB, k<=8` schedule and previous next-panel
prefetch path. The final rows are the new `production_auto` path.

| n | pre-change production | final production | speedup | final throughput |
|---:|---:|---:|---:|---:|
| 1024 | 1.4837 ms | 0.8372 ms | 1.77× | 2.565 Tops/s |
| 2048 | 5.8004 ms | 4.6234 ms | 1.25× | 3.717 Tops/s |
| 4096 | 40.856 ms | 32.859 ms | 1.24× | 4.183 Tops/s |

### Final production vs legacy schedule after the prefetch change

These rows isolate the final table-size policy from the now-shared single-table
execution path. At `n=1024`, the legacy `k=8` schedule remains slightly faster in
this run, but both rows are inside the M4RI 1.5× target; at `n=2048` and `n=4096`
the widened production policy wins.

| n | final production_auto | final legacy_64k_max8 | production / legacy |
|---:|---:|---:|---:|
| 1024 | 0.8372 ms | 0.7999 ms | 0.96× |
| 2048 | 4.6234 ms | 4.7870 ms | 1.04× |
| 4096 | 32.859 ms | 37.209 ms | 1.13× |

The repeat 4096-only run with a longer 5 s measurement window estimated
`production_auto/4096` at `[31.574 ms, 32.331 ms, 32.819 ms]`, confirming the
multi-size run was at the noisy edge rather than a one-off fast sample.

## M4RI target comparison

Pinned reference rows from `dev/bench_results/2026-04-29-strassen-matmul-crossover.md`
cite:

- `n=1024`: M4RI `3.020762 Tops/s`;
- `n=4096`: M4RI `6.272592 Tops/s`.

The 1.5× requirement means gf2 must reach at least two-thirds of those throughputs.

| n | final gf2 production throughput | M4RI reference throughput | gf2 / M4RI | M4RI / gf2 |
|---:|---:|---:|---:|---:|
| 1024 | 2.565 Tops/s | 3.020762 Tops/s | 0.849× | 1.18× |
| 4096 | 4.183 Tops/s | 6.272592 Tops/s | 0.667× | 1.50× |

For `n=4096`, the exact threshold from the pinned reference is `32.8665 ms`.
The final multi-size Criterion mean was `32.859 ms`, only barely within the
1.5× criterion, and that run's upper confidence bound (`33.018 ms`) crosses the
threshold. The longer 4096-only repeat is the stronger support row: its middle
estimate was `32.331 ms` and its full interval `[31.574 ms, 32.819 ms]` stayed
under the threshold. This is sufficient same-session evidence to land the
production improvement, but the margin is still narrow enough that future
pinned CI/perf runs should track the row explicitly.
