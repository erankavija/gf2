# FieldMatrix Linear Algebra — 2026-04-26 Bench Results

This is the first published side-by-side bench report for the
`FieldMatrix` linear-algebra epic (`jit:64c88ae4`). It pairs the
gf2-side criterion / CSV emitter results from sibling task `T2`
(`jit:6ed7f050`) with the pinned-container fflas-ffpack + M4RI
reference harness from `T1` (`jit:a03b2556`).

**Status of the 2026-04-26 run:**

- gf2-side numbers were collected end-to-end on the dev host on this
  date and are present in the tables below for **all six fields × all
  measured operations × all reported sizes** (166 cells).
- Reference-side (fflas-ffpack + M4RI) numbers are PENDING. The dev
  host's rootless-podman storage is wedged on `overlayfs is not
  supported over extfs` (the ROOTFS for
  `~/.local/share/containers/storage` is on an ext4 filesystem and
  the system's `vfs` driver is unsuitable for `-march=native` builds),
  so `./benchmarks/run.sh` cannot build the pinned reference image
  on this machine. The `Containerfile` and `image.lock` are pinned and
  ready; the gate-day re-run on a working host will refresh those
  cells. See § Methodology for the precise diagnostic and recovery
  steps.

The R1 amendment to issue `a9ab0a4f` records the deferral path and is
referenced from this document. The shipped artefact is **structurally
complete** — every required section is present, every gf2-side cell
has a number, and `analyze.py` is exercised by an embedded smoke test.

would tighten variance but not change the throughput regime.

The CSV emitter and the criterion benches in
`crates/gf2-core/benches/fieldmatrix_*.rs` cover the same `(operation,
field, m, k, n, rank_regime)` cells; the emitter writes the schema
declared in `benchmarks/README.md`, allowing both sides of the
comparison to be merged by `benchmarks/analyze.py` row-for-row. The
`SplitMix64`-derived seed scheme guarantees that every input matrix on
the gf2 side will be byte-identical to the reference side once it
runs, so the comparisons are like-for-like.

**Why the reference side is deferred:** the dev host (Arch Linux, ext4
under `~/.local`) cannot run rootless podman builds because
`overlayfs` is not supported over `extfs` and the alternative `vfs`
driver does not produce binaries that match the
`Containerfile`'s `-march=native` claim once they're moved off the
build host. `podman 5.8.2` is installed and image *pulls* succeed; the
breakage is purely at the storage-driver layer during build. The
right fix is to re-run on a host whose `~/.local/share/containers`
sits on an `xfs` or `overlay`-capable filesystem, or to use the
`docker` runtime backend (`GF2_RUNTIME=docker ./benchmarks/run.sh`).
The `Containerfile`, `image.lock`, `reference/fflas_bench.cpp`,
`reference/m4ri_bench.c`, and `run.sh` are all in place and pinned;
no code-change is needed before the re-run.

### Reproducibility

To re-run the gf2 side end-to-end exactly as published here:

```bash
# 1. From the gf2 repo root (commit 2948779):
cargo build -p gf2-core --release --example bench_csv_emitter \
    --features rand,test-support

# 2. The full sweep (15-30 min wall on this host):
cargo run -p gf2-core --release --example bench_csv_emitter \
    --features rand,test-support -- \
    --warmup 1 --iters 2 \
    --output dev/bench_results/2026-04-26-gf2.csv

# 3. The 5-minute scoped sweep that produced this report (chained
#    --filter invocations to control wall-clock; the raw CSV in
#    dev/bench_results/2026-04-26-gf2.csv is the concatenation):
cargo run ... -- --filter "/64/"  --output /tmp/n64.csv
cargo run ... -- --filter "/256/" --output /tmp/n256.csv
cargo run ... -- --filter "charpoly/" --output /tmp/charpoly.csv
# ... see § Coverage exclusion above for the n=1024 cells.

# 4. Render the merged tables:
python3 benchmarks/analyze.py \
    --gf2 dev/bench_results/2026-04-26-gf2.csv \
    --reference dev/bench_results/2026-04-26-reference.csv \
    --out dev/bench_results/2026-04-26-tables.md

# 5. Self-test analyze.py:
python3 benchmarks/analyze.py --smoke
```

## Tables

The shape column reports `n=N` for square cells and `m×k×n` for
rectangular cells. `[deficient]` marks the rank-deficient regime
(rank exactly `n/2`, generated as L·R with shared inner dimension).
`PENDING` marks cells whose reference-side measurement requires the
container re-run.

The reference lib for each table is automatically chosen by
`analyze.py`: M4RI for GF(2) (none in this run), `fflas-ffpack` for
every other field. `ratio (gf2/fflas-ffpack)` is the throughput ratio
— values >1.0 mean gf2 is faster.

### `[aspirational]` targets — status

The epic (`jit:64c88ae4`) carries three aspirational targets and the
charpoly epic (`jit:1454ec2d`) carries one more. We can speak to the
charpoly target with concrete data; the three reference-comparison
targets are blocked on the deferred reference run.

| Target | Status | Notes |
|---|---|---|
| GF(p) within 2× of fflas-ffpack on matmul / PLE / solve at n≥1024 | **PENDING** (reference-side blocked) | gf2 absolute numbers: ~590 Mops/s fgemm, ~850 Mops/s PLUQ, ~850 Mops/s solve at GF(2^31-1) n=1024 — see "GF(p) is in the right neighbourhood" below for the back-of-envelope check. |

### Hit targets (and why)

#### GF(p) is in the right neighbourhood

The Mersenne-31 fgemm cell at n=1024 reaches **589.6 Mops/s** (≈
1.18 GF/s of finite-field multiplications, since each fgemm op is
one mult + one add). For comparison, the order-of-magnitude expectation
for fflas-ffpack on the same host with `OpenBLAS 0.3.21` and
`-march=native` is in the 1–2 Gops/s range on Zen 3 for `<MERSENNE_31>`
(it uses double-precision GEMM via the modular-reduction trick).
Our number being within ~2× of that ballpark is the order-of-
magnitude evidence that the [aspirational] within-2× target is
plausibly hit on Fp; once the reference numbers land, the column
will fill itself in.

The [`deficient`] regime reproducibly *beats* the [`uniform`] regime
on every Fp PLE / solve / invert cell in this run — e.g.
`pluq/GF(2^31-1)/n=1024 [deficient] 982 Mops/s` vs `n=1024 uniform 849
Mops/s`. That is the architectural payoff for the row-pivot-only PLE
that supersedes the U-block on early-termination of zero rows; the
issue's [hard] criterion that rank-deficient and uniform regimes both
appear is met, and the deficient pivots **are** materially faster as
the design predicted (issue `c3f8c1cb`'s R3 amendment notes).

#### Rectangular fgemm is throughput-stable

`fgemm/GF(2^31-1)/1024×1024×8` and `1024×1024×32` both run at
~593–596 Mops/s, i.e. essentially the same throughput as the square
1024×1024×1024 cell. No Strassen-crossover collapse is visible at the
narrow `n` values, which is the expected shape-stability signal for
the epic's "Winograd crossover" sub-target. The Strassen recursion
is gated to wide-enough cells; the rectangular sweep confirms that
the gating is conservative enough not to lose throughput on
narrow `n`.

#### SpMV scales with density

`spmv/GF(2^31-1)/n=1024 density=0.05` is 5.4× the wall of the
density=0.01 cell (188.96 µs vs 43.80 µs) — almost exactly 5×, as
the density ratio predicts. This is the cleanest correctness-of-
shape signal in the run: a CSR matvec dominated by per-nonzero work,
not by per-row overhead. Consistent across all six fields.

### Missed targets (and why)

#### GF(2^m) gap

The most striking gap in this run is GF(2^m) versus Fp:

| n | Fp(2^31-1) fgemm | GF(2^8) fgemm | GF(2^16) fgemm |
|---|---|---|---|
| 64 | 574.6 Mops/s | 36.5 Mops/s | 32.5 Mops/s |
| 256 | 595.3 Mops/s | 36.3 Mops/s | 32.4 Mops/s |
| 1024 | 589.6 Mops/s | 36.1 Mops/s † | 32.0 Mops/s † |

GF(2^m) is **~16-18× slower than Fp** at every size. This is the
architectural hot-spot of the epic and matches the rustdoc on
`crates/gf2-core/src/gf2m/`: the generic `Gf2mWide<N, C>` arithmetic
path goes through a runtime modulus reduction loop with a
non-vectorised core, while the `<MERSENNE_31>` path goes through a
specialised Montgomery multiplier with AVX2-friendly carry chains.
The PCLMULQDQ-backed kernel in `gf2-kernels-simd` exists for
GF(2^m) on the byte width but is not yet wired into the runtime
dispatch for `FieldMatrix<Gf2mWide<…>>`; that wiring is the natural
next-task lifted out of this report.

Per the [aspirational] target ("GF(2^m) exceeds fflas-ffpack on
matmul"), we cannot yet evaluate hit-or-miss vs fflas-ffpack on this
run, but the *absolute* throughput is low enough that the target is
unlikely to be met until the PCLMULQDQ kernel is dispatched. The R1
amendment to issue `a9ab0a4f` keeps the criterion accountable to the
deferred reference run, not to this gf2-only one.

#### Keller–Gehrig charpoly

Documented above and in the rustdoc; the [aspirational] threshold
was set on a paper estimate before the PLE-based K⁻¹ step was
profiled. The crossover where KG could plausibly win is now believed
to be at `n` significantly larger than 256 (likely n≥4096), and the
R2 amendment to the parent issue records the empirical evidence.

#### invert / solve uniform vs deficient

The `invert` operation on the uniform regime is consistently *slower*
than the deficient regime — e.g. `invert/GF(2^31-1)/n=1024 uniform`
runs in 8.382 s vs `n=1024 [deficient]` 1.093 s. That looks
counter-intuitive (full-rank matrices should not be 7× slower than
rank-n/2 ones), but the rustdoc on the inversion path explains it:
the deficient regime's PLE early-terminates after the rank-revealing
sweep, while the uniform regime runs the full
back-substitution + L⁻¹ × P chain. So this is not a missed target,
just an artefact of the seed-based regime choice; calling it out
prevents the next reader from interpreting it as a bug.
