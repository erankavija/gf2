## § 1 — Cost Decomposition and Root Cause

### Root Cause (from `6613abf4` evidence doc § 7)

At GF(65521)/n=64, the `6613abf4` blocked-TRSM dispatch activates (`F::has_simd_gemm_classical()` returns true, `n=64 >= TRSM_BLOCKED_PANEL_SIZE=64`), but immediately falls back to the scalar `trsm_upper_inner` / `trsm_lower_inner` because the first line of the blocked inner function is:

```rust
if block_size == 0 || m <= block_size {
    trsm_upper_inner(a, b);
    return;
}
```

At n=64 with `block_size=64`, `m <= block_size` is `true` (64 ≤ 64), so the blocked path is bypassed. The recursive bisection in `trsm_upper_inner` then generates update GEMMs of shape 32×32×1 = 1024, 16×16×1 = 256, etc. — all below `GEMM_AXPY_FAST_PATH_THRESHOLD = 4096`.

### The Medium-Prime Sub-Path Gap

The `gemm_axpy_into_view` function has two SIMD fast paths:
1. **Small-prime whole-GEMM path**: packs A, runs byte-lane AVX2 GEMM. Threshold: `m*k*n >= 4096`.
2. **Medium-prime per-cell packed-dot path**: packs A and B^T once, then runs `try_fp_simd_dot_packed_u16` per cell. Same threshold: `m*k*n >= 4096`.

The threshold was applied equally to both paths with the comment "below this the per-cell `dot_product_slices` is competitive with pre-pack". This comment was **incorrect for the medium-prime case**: `dot_product_slices` calls `try_fp_simd_dot_product`, which allocates two fresh `Vec<u16>` scratch buffers on every single call. For a 32×32×1 GEMM with 32 output cells, this means 64 Vec allocations per GEMM call, vs 0 with pre-pack-once.

At n=64 the TRSM recursion generates O(n/8) ≈ 8 GEMM calls at various sizes (32×32×1, 16×16×1, ...), each with O(m) cells and O(m) Vec allocs. The cumulative allocation overhead explains why the n=64 solve was 2.10× vs fflas despite the blocked dispatch theoretically being active.

### Fix

Remove the `m * k * n < GEMM_AXPY_FAST_PATH_THRESHOLD` gate **from the medium-prime pre-pack path only**. The small-prime whole-GEMM threshold stays at 4096 (it calls a different kernel with different cost structure). The medium-prime pre-pack path always activates when `try_pack_fp_medium_u16` succeeds.

The pack cost is O(mk + kn) per call — amortised O(1) per output cell. For k=32, m=32, n=1: pack cost is 32×32 + 32×1 = 1,056 u16 pushes vs 32 × 2 Vec allocs saved. The pre-pack is always strictly cheaper for any `m >= 1` and `n >= 1`.

## § 2 — Fix Implementation

**File modified**: `crates/gf2-core/src/field/matrix.rs`

**Change**: In `gemm_axpy_into_view`, the medium-prime pre-pack section previously started:
```rust
let medium_pack_ok = if m * k * n < GEMM_AXPY_FAST_PATH_THRESHOLD {
    false
} else {
    // ... probe + pack
};
```

After the fix:
```rust
let medium_pack_ok = {
    // No lower-bound threshold: pre-packing A and B^T once is always cheaper
    // than per-cell scratch allocation in dot_product_slices.
    // (See jit:9138d86c evidence doc § 1 for the cost decomposition.)
    // ... probe + pack
};
```

The doc comment for `gemm_axpy_into_view` was also updated to document the asymmetry between the small-prime whole-GEMM threshold (kept) and the medium-prime per-cell threshold (removed).

**No changes to** `triangular.rs`, `inverse.rs`, or `TRSM_BLOCKED_PANEL_SIZE`. The blocked-TRSM dispatch and panel threshold are unchanged; the fix operates entirely within `gemm_axpy_into_view`.
